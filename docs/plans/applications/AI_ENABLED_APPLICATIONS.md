# Build an AI-enabled application path

> **Mission:** let an application keep ownership of its meaning while it communicates with an AI-capable service.

**Route:** name application concepts → connect them structurally → cross the service boundary → decide what the response means.

## Your route

1. **Keep meaning local.** Start with [ProtocolAi](https://github.com/TrentBest/TheSingularityWorkshop.ProtocolAi) to learn the application-owned vocabulary and deterministic address-space approach.
2. **Connect concepts.** Continue through [GrammarAi](https://github.com/TrentBest/TheSingularityWorkshop.GrammarAi) for structures that connect those identities.
3. **Reach a configured endpoint.** Explore [HeadlessAi](https://github.com/TrentBest/TheSingularityWorkshop.HeadlessAi) for its documented headless input-to-response path.
4. **Inspect orchestration projects.** Browse [CommandAi](https://github.com/TrentBest/TheSingularityWorkshop.CommandAi) and [CiAi](https://github.com/TrentBest/TheSingularityWorkshop.CiAi), then use their current READMEs to establish exact scope.
5. **Trace the boundary.** Record which component owns input, meaning, request formation, transport, response interpretation, and deterministic execution.

## Checkpoints

- Does the application own the concept, or is it merely a provider-specific prompt string?
- Which component actually sends the request?
- What evidence shows the response was interpreted and acted on?
